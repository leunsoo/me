## 세 줄 요약

- 이 사이트 글은 원래 `fs` + `gray-matter` + `next-mdx-remote` 40줄로 직접 읽었다. 파일이 4개일 땐 이걸로 충분했다.
- 읽기 시간·이전/다음·태그·시리즈·백링크·RSS·다국어 폴백을 붙이려니 이 위에 직접 얹기가 버거워져서 **Velite**로 갈아탔다.
- Next 16은 Turbopack이 기본이라 `VeliteWebpackPlugin`이 안 먹혔다. `velite --watch`를 `next dev` 옆에서 따로 돌리는 방식으로 우회했다.

> Claude와 같이 작업하며 정리한 글이다. 잘못된 표현이 있으면 알려주시면 감사하겠습니다.

## 파일이 4개일 땐 손으로 읽어도 됐다

이 사이트엔 작업실이랑 블로그가 있고, 글은 전부 `.mdx` 파일이다. 처음엔 이렇게 읽었다.

```ts
// src/lib/mdx.ts — 대충 이런 40줄
const files = fs.readdirSync(dir).filter((f) => f.endsWith(".mdx"));
return files.map((file) => {
  const raw = fs.readFileSync(path.join(dir, file), "utf-8");
  const { data, content } = matter(raw); // gray-matter
  return { slug: file.replace(/\.mdx$/, ""), frontmatter: data, content };
});
```

`fs`로 폴더 읽고, `gray-matter`로 frontmatter 떼고, 본문은 `next-mdx-remote`에 넘겨서 렌더. 끝. 글이 4개뿐이라 아무 불만이 없었다.

## 욕심이 화근이었다

그러다 붙이고 싶은 게 늘었다.

- 읽기 시간
- 이전 글 / 다음 글
- 태그 모아보기, 시리즈
- 관련 글
- 글끼리 링크 + 백링크 (누가 이 글을 링크했는지)
- RSS
- 다국어 (번역 없으면 한국어로 폴백)

문제는 이걸 전부 `fs` 위에 직접 얹어야 한다는 거였다. 관련 글이나 백링크는 글 하나 볼 때마다 전체 글이랑 비교해야 하는데(`O(n²)`), 이걸 요청마다 하면 느리다. 빌드 때 한 번만 계산해서 어딘가 저장해두는 구조가 필요했다. frontmatter 타입도 손으로 선언하고 있었어서, 필드 하나 오타 내면 런타임에서야 터졌다.

정리하면 **검증 + 타입 + 빌드 타임 파생 데이터**가 필요했는데, 이걸 다 직접 만들면 그게 그냥 작은 프레임워크다.

## 왜 Velite였나

콘텐츠 툴 하면 보통 Contentlayer가 먼저 떠오르는데, 원본은 사실상 방치 상태고 `contentlayer2` 커뮤니티 포크로 겨우 연명 중이다. Next 16이면 특히 불안하다.

**Velite**는 Zod 기반이고, 번들러에 안 묶여 있고, 아직 활발히 유지보수된다. 하는 일은:

- frontmatter를 Zod 스키마로 검증. 필드 빠지면 **빌드가 실패**한다 (런타임 아님).
- 스키마에서 타입 자동 생성. 손으로 선언한 타입이 실제랑 어긋날 일이 없다.
- `s.mdx()`, `s.metadata()`(읽기 시간), `s.toc()` 같은 내장 헬퍼.
- `prepare` 훅 — 여기서 이전/다음, 관련 글, 백링크를 **빌드 때 한 번** 계산해서 결과물에 구워버린다.

`O(n²)` 걱정하던 게 `prepare` 안으로 들어가니 그냥 없어졌다.

## Turbopack에서 한 번 자빠졌다

Velite 문서엔 "`next.config`에 `VeliteWebpackPlugin` 넣으면 끝"이라고 되어 있다. 그거 넣고 `npm run dev` 했더니 아무 일도 안 일어났다. (한참 헤맸다..)

이유: **Next 16은 `next dev`도 `next build`도 Turbopack이 기본**인데, Turbopack은 웹팩 플러그인을 안 받는다. 플러그인 API 자체가 다르다.

우회는 간단했다. Velite를 Next 빌드에 끼우지 말고 그냥 따로 돌린다.

```json
"dev": "run-p dev:content dev:next",
"dev:content": "velite --watch",
"dev:next": "next dev",
"build": "run-s build:content build:next"
```

`velite --watch`가 `src/content/`를 지켜보다가 바뀌면 데이터를 다시 뽑고, `next dev`는 그거랑 별개로 돈다. 빌드는 순서만 맞추면 된다 (velite 먼저, next 나중).

처음엔 "이거 좀 지저분한데" 싶었는데, 생각해보니 Prisma `generate`나 GraphQL codegen이랑 똑같은 패턴이다. 코드젠 도구는 원래 이렇게 dev 서버 옆에서 따로 돈다. 웹팩 플러그인이 편의였던 거지 정석이 아니었던 거다.

## 다국어 폴백을 무슨 언어로 안내할까

번역이 없는 글에 `/en/`으로 들어오면 한국어 본문을 대신 보여준다. 이때 위에 배너를 하나 다는데, 이 배너를 무슨 언어로 쓸까?

- 요청한 언어(영어)로? → 그 언어 번역이 없어서 이 상황인 건데 배너만 영어로 쓰는 것도 이상하다.
- 어차피 지금 화면에 뜨는 본문은 한국어다.

그래서 **폴백 언어(한국어)로** 썼다.

> 아직 영어 번역이 없는 글입니다. 한국어 원문으로 표시합니다.

여기에 `noindex`를 걸고 (구글이 이 페이지를 영어 페이지로 착각해 색인하면 중복 콘텐츠가 된다), `canonical`은 실제 한국어 원문을 가리키게 했다. 번역을 올리면 배너랑 `noindex`가 자동으로 사라진다.

## 그래서 뭐가 좋아졌나

- frontmatter 오타 → 빌드에서 잡힌다.
- 읽기 시간, 이전/다음, 관련 글, 목차, 태그 페이지, 시리즈, 백링크, RSS, 사이트맵 전부 붙었다.
- 관련 글·백링크 계산은 빌드 때 한 번.
- `src/lib/mdx.ts` 40줄이랑 `src/features/workshop/` 폴더를 통째로 지웠다.

## 배운 점

**"글이 몇 개부터 툴 쓰나요"는 틀린 질문이었다.** 순수 산문이면 300개여도 `fs`로 충분하다. 나를 갈아타게 만든 건 개수가 아니라 검증·파생 데이터·다국어 같은 **복잡도의 종류**였다.

**툴 통째로 들이기 전에 중간 단계가 있었다.** `fs` 코드 안에서 Zod 검증만 얹어도 "검증 + 타입 한 곳"은 얻는다. 이번엔 파생 데이터 때문에 Velite까지 갔지만, 검증만 필요했으면 거기서 멈춰도 됐다.

**placeholder 도메인은 위험하다.** RSS랑 사이트맵엔 절대 URL이 필요해서 가짜 도메인을 잠깐 박아뒀는데, 이런 건 잊어버리면 그대로 배포돼서 피드에 나간다. 환경 변수로 빼고 폴백을 실제 도메인으로 바꿔뒀다.
