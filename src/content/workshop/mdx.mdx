## 개요

**MDX 는 Markdown 과 JSX 를 합친 형식입니다.**\
평범한 마크다운 문서 안에 리액트 컴포넌트를 그대로 써 넣을 수 있고, 파일 확장자는 `.mdx` 를 씁니다.

```mdx
# 오늘 해야 할 일

<Todo data={todos} />

**결론**: 화이팅!
```

`#` 과 `**` 는 평소처럼 마크다운으로 변환되고, `<Todo />` 는 빌드 시점에 실제로 렌더되는 컴포넌트입니다.\
즉 **내용은 내용대로 쓰고, 필요한 지점에만 컴포넌트를 박는 형식**입니다.\
지금 읽고 계신 이 글도 `.mdx` 파일 한 개이며, 뒤에서 설명드릴 과정을 통해 이 페이지가 되었습니다.

## 현재 구조

글은 전부 `src/content/` 아래 위치하며, 파일을 새로 생성하면 목록과 라우트에 자동으로 잡히는 구조입니다.

```
src/content/workshop/mdx.mdx
        │
        │  ① fs 로 폴더 읽기 · 정형화된 객체 반환 (src/lib/mdx.ts)
        ▼
{ slug: "mdx", frontmatter: { title, summary, date }, content: "## 개요..." }
        │
        │  ② 반환된 값을 통해 generateStaticParams 로 slug 마다 정적 경로 생성    (app/[locale]/workshop/[slug]/page.tsx)
        ▼
<MDXRemote source={content} ... />
        │
        │  ③ 빌드 타임에 MDX → 리액트 트리로 컴파일 (next-mdx-remote/rsc)
        ▼
렌더된 정적 HTML
```

## MDX를 쓰는 이유

마크다운은 글쓰기에는 좋지만 "글에 인터랙티브한 예제를 넣고 싶다" 가 불가능합니다. 인터렉티브한 요소를 넣으려면 결국 컴포넌트를 렌더해야 합니다.\
컴포넌트를 넣겠다고 본문 전체를 JSX 나 HTML 로 쓰면 작성자 입장에서 코드의 가독성이 현저히 떨어집니다.

## Next.js에서 MDX 적용 방법

MDX 를 Next.js 에 적용하는 방식은 크게 둘입니다.

| 방식              | 형태                                       | 언제                                |
| ----------------- | ------------------------------------------ | ----------------------------------- |
| **파일 = 페이지** | `@next/mdx` 설정 후 `app/about/page.mdx`   | 페이지 하나가 통째로 글일 때        |
| **콘텐츠 컬렉션** | `content/` 에 `.mdx` 를 모으고 코드가 스캔 | 글이 여러 개, 동적 라우트로 뿌릴 때 |

이 프로젝트는 다음과 같은 이유들로 콘텐츠 컬렉션 방식을 채용했습니다.

- 작업실 글이 여러 개이고, 앞으로 계속 늘어날 예정입니다. `[locale]/workshop/[slug]` 라우트 하나가 전부를 처리할 수 있습니다.
- 글 목록 페이지는 본문을 렌더하지 않고 frontmatter(`title`·`summary`·`date`)만 필요한데, 컬렉션 방식은 이 둘을 분리해 읽을 수 있습니다.
- 현재 `[locale]` 세그먼트 아래에 있어야 다국어 라우팅을 지원하는데, `page.mdx` 는 해당 구조에 적합하지 않습니다.

### 툴(Contentlayer·Velite) 이 아니라 직접 읽는 이유

컬렉션 방식은 다시 **직접**(`fs` + `gray-matter` + `next-mdx-remote`) 과 **툴**(`Contentlayer`·`Velite` 가 스캔·타입 생성·스키마 검증까지 대행) 로 나뉩니다. 글이 네 개인 지금은 `src/lib/mdx.ts` 40줄이면 충분해서 직접 읽습니다. frontmatter 타입은 `WorkshopFrontmatter` 로 손수 선언합니다.

### 빌드 타임 컴파일

`generateStaticParams` 로 slug 마다 페이지를 미리 만들고, MDX 컴파일도 그때 끝납니다. 런타임에는 정적 HTML 만 나가고, 마크다운 파서가 클라이언트 번들에 들어가지 않습니다.

### 언제 MDX 를 쓰지 말아야 하나

인터랙티브 요소가 전혀 없는 글이라면 MDX 는 과합니다. 순수 산문은 `.md` 로 충분하고, 그 편이 파서·컴파일 부담도 없습니다. MDX 는 "이 문서에 컴포넌트가 필요하다" 가 참일 때만 값을 합니다.

## 개념과 사용법

### 마크다운은 그대로

제목 `#`, 굵게 `**`, 목록 `-`, 링크 `[텍스트](url)`, 인라인 코드는 백틱, 코드 블록은 백틱 세 개. `remark-gfm` 을 붙였으므로 표·취소선·`- [ ]` 체크리스트도 됩니다.

### 컴포넌트 넣기

두 가지 경로가 있습니다.

```mdx
import { Callout } from "./Callout";

<Callout type="warning">이 안에서도 **마크다운**이 동작합니다.</Callout>
```

첫째는 파일 안에서 직접 `import`. 둘째는 렌더러에 **컴포넌트 맵**으로 넘기는 방식이고, 이 프로젝트가 쓰는 쪽입니다.

```tsx
// src/features/workshop/mdx-components.tsx
export const workshopMdxComponents: MDXComponents = {
  DesignSystemCatalog,
};

// page.tsx
<MDXRemote source={doc.content} components={workshopMdxComponents} />;
```

맵에 올린 이름은 본문에서 그냥 `<DesignSystemCatalog />` 로 쓰면 됩니다. `import` 줄이 필요 없습니다.

> RSC(`next-mdx-remote/rsc`)에서는 `@mdx-js/react` 의 `MDXProvider` 컨텍스트로 컴포넌트를 주입할 수 없습니다. 서버 컴포넌트가 React Context 를 지원하지 않기 때문입니다. 반드시 `components` prop 으로 넘깁니다.

표준 태그(`h2`·`a` 등)도 이 맵으로 오버라이드할 수 있지만, 이 프로젝트는 그렇게 하지 않고 `.prose` CSS 로 스타일링합니다.

### 표현식 `{ }`

```mdx
2 + 2 = {2 + 2}

export const author = "이은수";

글쓴이: {author}
```

중괄호 안은 그냥 JavaScript 입니다. `export` 로 이 파일 스코프의 상수·컴포넌트를 정의할 수도 있습니다.

### Frontmatter

파일 맨 위 `---` 로 감싼 YAML 블록입니다. 제목·요약·날짜 같은 메타데이터를 담습니다.

```mdx
---
title: "MDX"
summary: "마크다운 + JSX…"
date: "2026-09-01"
---

여기부터 본문.
```

**Frontmatter 는 MDX 자체 기능이 아닙니다.** 파싱하는 쪽이 떼어내 처리합니다. 이 프로젝트는 `gray-matter` 가 MDX 컴파일 전에 분리해 `frontmatter` 객체와 `content` 문자열로 나눕니다. (`next-mdx-remote` 의 `parseFrontmatter` 옵션은 쓰지 않습니다 — `gray-matter` 로 이미 처리했기 때문입니다.)

### 컴파일 파이프라인

MDX 컴파일러는 `.mdx` 를 **리액트 컴포넌트를 export 하는 JS 모듈**로 바꿉니다. 중간 두 지점에서 개입할 수 있습니다.

- **remark 플러그인** — 마크다운(mdast) 단계. 예: `remark-gfm`(표 지원). 이 프로젝트가 `options.mdxOptions.remarkPlugins` 로 넘기는 지점.
- **rehype 플러그인** — HTML 트리(hast) 단계. 예: `rehype-slug`(제목에 `id`), `rehype-pretty-code`(코드 구문 강조). 아직 안 씀.

### 서버 / 클라이언트 경계

`next-mdx-remote/rsc` 의 `<MDXRemote>` 는 async 서버 컴포넌트라 서버에서만 렌더됩니다. 본문에 임베드한 컴포넌트도 기본은 서버 컴포넌트로 취급됩니다. `useState`·`onClick` 등이 필요하면 그 컴포넌트 파일에 `"use client"` 를 붙여 클라이언트 컴포넌트로 만들고, 그걸 맵에 올립니다. (`DesignSystemCatalog` 는 상호작용이 없어 서버 컴포넌트입니다.)

### 스타일 누수와 `.not-prose`

본문 전체에 `.prose` 를 걸면, 그 안에 임베드한 컴포넌트 내부의 `h2`·`p`·`a` 까지 `.prose` 규칙이 새어듭니다. 이 프로젝트는 `.prose` 의 모든 선택자에 `:not(.not-prose *)` 가드를 걸어 두었고, 위젯을 `<div className="not-prose">` 로 감싸면 스타일이 차단됩니다. `DesignSystemCatalog` 가 최상위를 `not-prose` 로 감싸는 이유입니다.

### 이스케이프 주의

- **`<` 와 `{` 는 특수문자입니다.** 본문에 그냥 쓰면 JSX 태그나 표현식으로 해석됩니다. 리터럴로 남기려면 백틱이나 코드 펜스 안에 넣습니다.
- **HTML 주석(`<!-- -->`)은 MDX 에서 동작하지 않습니다.** 주석은 `{/* ... */}` 로 씁니다.

### 정리

| 개념            | 요점                                                           |
| --------------- | -------------------------------------------------------------- |
| MDX             | 마크다운 문법 + 본문에 렌더되는 JSX 컴포넌트                   |
| 컴포넌트 주입   | `import` 또는 `components` 맵. RSC 는 맵만 가능                |
| `{ }`           | 중괄호 안은 JavaScript. `export` 로 스코프 상수 정의           |
| frontmatter     | MDX 밖 기능. `gray-matter` 가 컴파일 전에 분리                 |
| remark / rehype | 마크다운 단계 / HTML 트리 단계 개입 지점                       |
| 서버/클라       | `<MDXRemote>` 는 서버 전용. 상호작용 컴포넌트엔 `"use client"` |
| `.not-prose`    | `.prose` 스타일이 임베드 위젯으로 새는 것을 차단               |
| 언제 안 쓰나    | 인터랙티브 요소가 없으면 `.md` 로 충분                         |

관련 파일: `src/content/workshop/*.mdx`, `src/lib/mdx.ts`, `src/features/workshop/{entries.ts,mdx-components.tsx}`, `src/app/[locale]/workshop/[slug]/page.tsx`, `src/styles/globals.css` 의 `.prose`.
